# رفع توقف بازیابی پیش‌نویس رویا

## شواهد
- بررسی صف واقعی رویا: آیتم‌های failed فاقد failure_stage و شناسه درخواست تصویر شده بودند، در حالی که فایل‌های پیش‌نویس همان آیتم‌ها اطلاعات مرحله تصویر را داشتند.
- عامل حذف، بازسازی allowlist قدیمی در automation/build_roya_queue.py بود. هر بار workflow صف را بازسازی می‌کرد، last_error، failure_stage، next_retry_at و مالکیت درخواست تصویر حذف می‌شدند؛ pick فقط خطاهای ظرفیتِ دارای این شواهد را انتخاب می‌کند.
- ممیزی آفلاین: 31 سابقه failed/image دارای key و generated_at کاملاً منطبق با صف موجود بود. با ترمیم محدود، هر31 برای بررسی مجدد ظرفیت قابل انتخاب شدند. این عدد تعداد تولید یا انتشار نیست.

## اصلاح
- حفظ صریح فیلدهای غیرمحرمانه وضعیت، تایمر، مالکیت درخواست، زمینه مقاله و سابقه QA تصویر در بازسازی صف.
- ترمیم داده‌های قبلاً حذف‌شده فقط از فایل پیش‌نویس failed با key و زمان تولید یکسان؛ سابقه منتشرشده، دارای pid/نشانی انتشار، قدیمی، ناسازگار یا نامعتبر بازیابی نمی‌شود.
- وضعیت/تعداد تلاش/نشانی مقصد تغییر نمی‌کند. timer موجود بر checkpoint قدیمی اولویت دارد. هیچ فیلد ناشناخته یا خصوصی کپی نمی‌شود.
- مسیر بازیابی ظرفیت همچنان فقط پیش‌نویس محفوظِ خطای ظرفیت را می‌پذیرد؛ خطای محتوایی/بصری/مجوز و مطالب منتشرشده خودکار تأیید نمی‌شوند. QA متن و تصویر نهایی، سقف صف و حوزه tape20 بدون تغییر است.
- تغییر سازنده صف و آزمون‌های آن اکنون workflow عادی رویا را فعال می‌کند. آزمون‌های بازیابی ظرفیت و بازسازی قبل از تولید اجرا می‌شوند؛ تولیدکننده رویا خود API تصویر نمی‌زند.

## وضعیت اصلاحات تصویر قبلی
- اجرای 39072973665 با هر دو مرحله tests و replenish موفق شد؛ 11 درخواست قرارداد قدیمی superseded شدند تا تصویر/چیدمان قدیمی بازاستفاده نشود. پس از آن3 درخواست جدید در صف مشاهده شد.
- این گزارش تأیید تصویر جدید یا انتشار نیست؛ تصویر دارای خط زیر بسته همچنان rejected است.
